# ADR-001: Linking Security Alerts to Parking Sessions

**Status:** Accepted  
**Date:** October 21, 2026  
**Project:** SmartPark Sentinel

## Context

SmartPark Sentinel is a parking security application designed to detect stolen vehicles, vehicles parked too long, missing license plates, and registration problems.

While developing my M3 domain model, I had to decide how security alerts should connect to other information in the system. A vehicle can enter a parking lot multiple times, and each visit may have different security problems.

I wanted the system to keep track of when and where an alert happened, instead of only connecting alerts to a vehicle.

## Decision

I decided to connect security alerts to parking sessions in my domain model.

Each alert can reference the parking session where the issue was detected. The alert can also reference a vehicle or watchlist entry when that information is available.

This allows the system to keep information about the specific parking event that caused an alert.

## Alternatives Considered

**Alternative 1: Connect security alerts directly to vehicles only.**

This would make it easier to find alerts related to a specific vehicle. However, it would be harder to identify which parking visit caused each alert. I did not choose this because one vehicle can have multiple parking sessions.

**Alternative 2: Store alerts without relationships to parking sessions or vehicles.**

This would make the alert system simpler at first. However, it would become difficult to investigate alerts because the system would not clearly identify the parking event involved. I rejected this option because SmartPark Sentinel needs useful records for security investigations.

## Consequences

**Positive consequences:**

- Security alerts can be traced to specific parking sessions.
- The system can maintain a history of incidents across different visits.
- Security staff can investigate when and where an issue occurred.
- Alerts can still be recorded when vehicle identification is incomplete.

**Negative consequences:**

- The database relationships become more complicated.
- Retrieving all alerts for a vehicle may require joining multiple tables.
- Developers must handle alerts that have missing vehicle or session information.
- Changing how parking sessions work in the future may require updates to the alert system.

## Conclusion

I chose this design because tracking the actual parking event is important for SmartPark Sentinel. Although it makes the data model more complicated, it provides better information for investigating security issues.
